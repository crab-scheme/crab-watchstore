# ADR 0004 — Auth / RBAC model

- **Status:** Accepted
- **Date:** 2026-06-10
- **Tracking:** `cw-u4a.25` (this ADR), implemented by `.26` (enforcement: token table + `Authenticate` + the per-request authz hook in `grpc-kv` + password verify), exposed by `.27` (the gRPC `Auth` service: `UserAdd/Delete/ChangePassword/Get/List`, `RoleAdd/Delete/GrantPermission/RevokePermission`, `AuthEnable/Disable`, `Authenticate`).
- **Builds on:** [ADR 0001 — MVCC data model](0001-mvcc-data-model.md). Auth records ride the same single column family / WAL / Raft group-commit as the keyspace (so they are replicated + crash-consistent + survive leader change for free), under a **new 5th namespace tag** `NS-AUTH` (`0x04`), disjoint from `META/KEY/REV/LEASE`. The mTLS hook `(grpc-request-peer-identity h)` (`cw-u4a.21`, `src/server/grpc-kv.scm`) supplies the cert identity. The apply seam `mvcc-apply` (`src/mvcc.scm`) and the per-request dispatch in `src/server/grpc-kv.scm` are the wiring points for `.26`.
- **Validated by:** [`test/auth-poc.scm`](../../test/auth-poc.scm) — **67 assertions, green twice back-to-back**, over the REAL store machinery (`store-ctx` + `mvcc` + the new [`src/auth.scm`](../../src/auth.scm)): the load-bearing range-containment permission check (single-key / prefix / all-keys / range / op-type / union-doesn't-stitch), the `NS-AUTH` storage round-trip for `User{name,hash,roles}` and `Role{name,perms}` (incl. a real Argon2id hash that verifies), **disjointness** (a client `mvcc-range` over all-keys returns the normal key and NEVER the auth records), the auth-revision counter, and the full `auth-authorize?` decision (root / auth-disabled / deny).

## Context

crab-watchstore is an etcd v3 API-compatible store. etcd's **authentication + RBAC** model is small and well-defined:

- A **user** has a name, a hashed password, and a set of roles.
- A **role** has a name and a set of **key-range permissions**.
- A **permission** is a `(permType, key, range_end)` triple where `permType ∈ {READ, WRITE, READWRITE}` and `[key, range_end)` is the half-open key range it grants (with etcd's usual single-key / prefix / all-keys sentinel conventions).
- There is a special **`root` role** (full access) and a **`root` user** (must hold the `root` role before auth can be enabled).
- A global **auth-enabled** flag gates the whole system: when off, every request is allowed (the store behaves exactly as today).
- A monotonic **auth-revision** (etcd's `authRevision`) bumps on **every** auth mutation, so clients can detect a stale auth cache / token.

Two ways a client proves identity:

1. **Token** — call `Authenticate(name, password)`; on success receive an opaque **token**, presented on every subsequent call in the gRPC **`token`** metadata header.
2. **Client-cert Common-Name** — etcd's `--client-cert-auth`: a verified client certificate whose **CN equals a username** authenticates AS that user with **no password and no token**. crab-watchstore already surfaces the verified CN via `(grpc-request-peer-identity h)` (`cw-u4a.21`).

Per request, the server resolves the identity → user → roles → permissions and checks the **requested key (or `[key, range_end)` for ranges)** against the union of the user's permissions for the operation's type. The crux of this ADR is getting that **range-containment check** exactly right, and storing the auth state so it is **replicated and survives leader change** without polluting the client-visible keyspace.

We build on the **already-built MVCC substrate** (ADR 0001):

- **Namespace tags** — the keyspace is one RocksDB CF split by a leading 1-byte tag (`NS-META 0x00`, `NS-KEY 0x01`, `NS-REV 0x02`, `NS-LEASE 0x03`); a prefix scan of one never bleeds into another, and sharing one CF means one WAL → one fsync → atomic multi-namespace writes (ADR 0001 §1). Auth takes the **next free tag, `NS-AUTH 0x04`**.
- **The apply seam** — `mvcc-apply ctx cmd` (`src/mvcc.scm`) runs inside the shard actor's group-commit batch; it is the single replicated point where committed state changes. Auth **mutations** go through here as new command cases (`.26`), exactly like `PUT` / `DEL` / `LEASE-*`.
- **The dispatch seam** — `src/server/grpc-kv.scm` `dispatch!` already reads `(grpc-request-path h)`, the decoded request (keys/ranges), and `(grpc-request-peer-identity h)`. This is where `.26` inserts the per-request authorization check.
- **The crypto stdlib** — `(crab crypto)` ships **Argon2id** password hashing (`crypto-password-hash` / `crypto-password-verify`), a CSPRNG token mint (`crypto-random-token`), and a timing-safe compare (`crypto-constant-time=?`). Confirmed present in the release binary.

### What this ADR must pin down

1. The **data model** (User / Role / Permission / root / auth-enabled) with etcd field/enum parity for the wire (`.27`).
2. The **storage encoding** under `NS-AUTH` (users, roles, the auth-enabled flag, the auth-revision counter), how a mutation is **applied through Raft**, and why this beats a reserved prefix inside `NS-KEY`.
3. The **password-hash scheme** (Argon2id) — how it is stored, how `.26` verifies it, and what (if anything) `.26` still needs.
4. **Authentication** — the token scheme (a simple leader-local token table), the `token` metadata header, and the **cert-CN** path.
5. **Authorization** — the load-bearing **range-containment** check, root / auth-disabled short-circuits, and the etcd error on deny / bad auth.
6. The **consumers** table mapping `.26` and `.27` to this design.

## Decision

### 1. Data model (etcd-parity)

```
User       := { name        : bytes          ; the login name
                password-hash: bytes          ; Argon2id PHC string ("" = no-password user)
                roles        : [role-name…] } ; granted role names

Role       := { name        : bytes
                permissions  : [Permission…] }

Permission := { permType     : READ | WRITE | READWRITE   ; etcd authpb.Permission.Type
                key          : bytes
                range_end    : bytes }                     ; "" single-key ; "\0" all ; prefixEnd prefix
```

- **`permType` enum values are wire-exact** with etcd `authpb.Permission.Type`: `READ = 0`, `WRITE = 1`, `READWRITE = 2` (`src/auth.scm`: `PERM-READ`/`PERM-WRITE`/`PERM-READWRITE`). `.27`'s protobuf codec passes the enum int straight through, the same trick `grpc-kv.scm` already uses for `Compare`/`SortOrder` enums.
- **`root` role + `root` user.** A user holding the role named **`root`** has **full access to everything** (the authorization check short-circuits to allow). `AuthEnable` is rejected unless a `root` user exists and holds the `root` role (etcd `ErrRootUserNotExist` / `ErrRootRoleNotExist`).
- **auth-enabled flag.** A single global boolean. **Off ⇒ every request is allowed** (identity is not even resolved) — the store behaves exactly as it does pre-auth, so turning auth on is opt-in and reversible.
- **`range_end` sentinels** are etcd's and match `mvcc.scm`'s existing `range-in-range?`: empty ⇒ **single key**; `"\0"` (one `0x00` byte) ⇒ **to end of keyspace** (and `key = "\0"` too ⇒ **all keys**); otherwise the half-open `[key, range_end)`. A **prefix** permission is `[key, prefixEnd(key))` where `prefixEnd` bumps the last non-`0xFF` byte (`mvcc.scm`'s `prefix-range-end`).

### 2. Storage — a dedicated `NS-AUTH` namespace, replicated through Raft

Auth state is written to the **durable, replicated store** so it survives leader change — but under a **new namespace tag**, **not** inside the client keyspace:

```
NS-AUTH 0x04   sub-split by a second tag byte ('M' < 'R' < 'U', disjoint ordered sub-ranges):
  user record :  0x04 ‖ 'U'(0x55) ‖ name   -> { hash, roles[] }   length-prefixed blob
  role record :  0x04 ‖ 'R'(0x52) ‖ name   -> { perms[] }          length-prefixed blob
  meta scalar :  0x04 ‖ 'M'(0x4D) ‖ name   -> scalar
     "enabled"   -> u8  (0/1)              ; the global auth-enabled flag
     "auth-rev"  -> u64                    ; the auth-revision counter (etcd authRevision)
```

**Record encodings** (self-describing length-prefixed blobs, the same style as ADR 0001 §4; `src/auth.scm` `auth-enc-user`/`auth-enc-role` + decoders, validated by the POC round-trip):

```
user-blob := u64be hash_len ‖ bytes hash ‖ u64be role_count ‖ role_count×( u64be name_len ‖ bytes name )
role-blob := u64be perm_count ‖ perm_count×( u8 permType ‖ u64be key_len ‖ bytes key ‖ u64be rend_len ‖ bytes range_end )
```

The user/role **name lives in the key** (so a `kv-scan` of `0x04‖'U'` enumerates every user for `UserList`, and `0x04‖'R'` every role for `RoleList`); the value carries the rest. Because `'M' < 'R' < 'U'`, the three sub-ranges are disjoint and a scan of one never returns another's rows.

**Why a side namespace, not a reserved prefix inside `NS-KEY`.** ADR 0001's `NS-KEY` is the *client-visible, MVCC-versioned, Watch-emitting* keyspace. Putting auth records there (e.g. under a `_auth/` user-key prefix, written via `mvcc-put!`) is the tempting "it just rides the existing MVCC store" option — and it is **wrong** here:

- `mvcc-put!` appends a **`NS-REV` Watch event** for every write, so a client `Watch` over all-keys would **stream every UserAdd / password change** — a direct disclosure of auth mutations.
- A client `Range` over all-keys (`key="\0", range_end="\0"`) scans **all of `NS-KEY`**, so it would **return the stored password hashes**. etcd specifically keeps auth out of the key bucket so `etcdctl get --prefix ""` cannot enumerate users.
- The MVCC per-key fields (`create_revision` / `version` / point-in-time reads) are **meaningless for auth** — you always want the latest user record — and coupling auth mutations to the keyspace `current-rev` is exactly what etcd's **separate `authRevision`** exists to avoid.

A dedicated tag gives **all the replication / crash-consistency / leader-survival** of the MVCC store (it is the same CF → same WAL → same one-fsync Raft group-commit) while keeping auth **invisible to `Range`/`Watch`** (which only ever scan `NS-KEY` / `NS-REV`) and **decoupled** from the keyspace revision. This is in fact closer to real etcd, which stores auth in separate backend buckets with its own `authRevision`. The POC asserts the security property directly: after writing a user "alice" *and* a normal keyspace key "alice", `mvcc-range` over all-keys returns **count = 1** (only the keyspace key), and the auth `UserList` never returns the keyspace key.

**Versioning.** "Versioned" here means the monotonic **auth-revision** (a single `NS-AUTH` meta scalar), which is etcd's `authRevision` — the axis clients cache against — **not** per-record MVCC history. etcd's `authpb` records carry no per-record revision either; the global `authRevision` is the whole version story. `src/auth.scm` `auth-rev` / `auth-bump-rev!`.

**How a mutation is applied (through Raft, like a `PUT`).** Each auth change is a single flat, node-send-safe command (bytevector list, decimal-ASCII scalars — the existing `mvcc-apply` convention), proposed through Raft and applied by a **new `mvcc-apply` case (`.26`)** that mutates `NS-AUTH` and **bumps `auth-rev` in the same group-commit batch**. Because it is one committed Raft entry applied **identically on every replica**, auth state is consistent across the cluster and **survives leader change with zero extra work** (the new leader just reads the replicated `NS-AUTH` records). The command vocabulary `.26` adds:

| Command (flat bytevectors) | Effect |
|---|---|
| `("AUTH-ENABLE")`  | guard: a `root` user with the `root` role must exist, else `ErrRootUserNotExist`/`ErrRootRoleNotExist`; set `enabled = 1`; bump `auth-rev` |
| `("AUTH-DISABLE")` | set `enabled = 0`; bump `auth-rev` |
| `("AUTH-USER-ADD" name hash)` | create user (reject if exists → `ErrUserAlreadyExist`); bump |
| `("AUTH-USER-DELETE" name)` | delete user; bump |
| `("AUTH-USER-CHPASS" name hash)` | replace password hash; bump |
| `("AUTH-USER-GRANT-ROLE" name role)` | add role to user; bump |
| `("AUTH-USER-REVOKE-ROLE" name role)` | remove role from user; bump |
| `("AUTH-ROLE-ADD" name)` | create role; bump |
| `("AUTH-ROLE-DELETE" name)` | delete role **and strip it from every user** (etcd semantics); bump |
| `("AUTH-ROLE-GRANT-PERM" role permType key rangeEnd)` | add permission to role; bump |
| `("AUTH-ROLE-REVOKE-PERM" role key rangeEnd)` | remove the matching permission; bump |

These **do NOT bump the keyspace `current-rev`** (auth mutations are not keyspace revisions — exactly as `LEASE-GRANT` doesn't, ADR 0003 §6). The POC asserts `auth-bump-rev!` advances the auth-revision while `mvcc-current-rev` is unchanged. `src/auth.scm` already provides the storage primitives these cases call (`auth-put-user!` / `auth-put-role!` / `auth-set-enabled!` / `auth-bump-rev!`); `.26` adds only the `mvcc-apply` dispatch + the per-command guards/validation.

### 3. Password hashing — Argon2id (better than etcd's bcrypt)

The crypto-stdlib survey (`crates/cs-stdlib-crypto`, `(crab crypto)`) found a **misuse-resistant, pure-Rust Argon2id** already shipped and working in the release binary:

- `(crypto-password-hash password)` → a self-describing **PHC string** (`$argon2id$v=19$m=…,t=…,p=…$salt$hash`) with a random per-password salt.
- `(crypto-password-verify password phc)` → boolean; a malformed hash returns `#f` rather than raising.

etcd uses **bcrypt**; Argon2id is the modern OWASP-recommended successor, so crab-watchstore is *stronger* than etcd here, not a downgrade. We store the **PHC string bytes** verbatim as the user record's `hash` field. The POC stores a real `crypto-password-hash "s3cret"`, round-trips it through `NS-AUTH`, and asserts the decoded bytes **verify** the original password and **reject** a wrong one.

**Determinism — the hash is computed once, on the leader.** Argon2id salts randomly, so hashing the same password on each replica would yield different bytes. Therefore the **gRPC handler on the proposing leader** computes `crypto-password-hash` and proposes `("AUTH-USER-ADD" name <phc-bytes>)`; every replica stores the **identical** bytes. Verification (`Authenticate`, `.26`) runs `crypto-password-verify` against the stored PHC on the serving leader. A **no-password** user (cert-CN-only, or etcd's `--no-password`) stores an empty `hash`; the POC round-trips that too.

**What `.26` needs from crabscheme:** for hashing — **nothing new**; `crypto-password-hash` / `crypto-password-verify` / `crypto-random-token` / `crypto-constant-time=?` all exist and are verified working. See §4 for the **one** missing builtin (metadata access), which is the only interpreter gap.

### 4. Authentication — simple token table + cert-CN

**Token scheme: a simple, leader-local token table** (etcd's default `simple` token, not JWT). On `Authenticate(name, password)`:

1. Read the user record from `NS-AUTH` (a leader-gated / ReadIndex read) and `crypto-password-verify` the password against the stored PHC. On mismatch → `ErrAuthFailed`.
2. Mint an opaque token with `(crypto-random-token 24)` (URL-safe, CSPRNG).
3. Store `token → (username . auth-rev-at-issue)` in a **leader-local in-memory table** (a `make-table` / hashtable in the `grpc-kv` actor — `.26`). The table is **not replicated**: a leader change drops it and the client simply re-`Authenticate`s (this is etcd's documented `simple` token behavior; tokens are leader-scoped).

The client presents the token on every call in the gRPC **`token`** metadata header. Per request `.26`: read the header, look up the table; if present **and** the user still exists **and** the cached `auth-rev` is not older than the current `auth-rev` (so an auth change can invalidate live tokens, etcd's `AuthOldRevision`), the request is authenticated as that user. A present-but-unknown/stale token → `ErrInvalidAuthToken`.

> JWT (stateless, signed, survives leader change) was considered and **declined for v1** as more than needed — but the stdlib already has everything to add it later (`hmac-sha256` in `(crab hash)`, or `crypto-ed25519-sign` in `(crab crypto)`). Recorded in Alternatives.

**Cert-CN path (etcd `--client-cert-auth` Common-Name auth).** `(grpc-request-peer-identity h)` returns the verified client-cert SAN/CN (or `#f` over h2c / no client cert). If that CN **equals a username**, the request is authenticated AS that user with **no token and no password**. Precedence `.26` applies:

```
token header present  → resolve via the token table (token identity wins)
else peer-identity CN  → if it matches a user, authenticate as that user
else                    → no identity (unauthenticated)
```

When auth is **disabled**, identity is never resolved (every request is allowed). The cert-CN path needs **no new builtin** — `grpc-request-peer-identity` already exists (`cw-u4a.21`).

**THE ONE INTERPRETER GAP `.26` MUST CLOSE.** The gRPC builtins (`crates/cs-runtime/src/builtins/grpc.rs`) expose `grpc-request-path`, `grpc-request-bytes`, and `grpc-request-peer-identity` — but **not request metadata**, so the **`token` header is not yet readable from Scheme**. `.26` must add a builtin, e.g. `(grpc-request-metadata h "token") → string | #f`, plumbed from `cs_web::grpc::GrpcRequest` (hyper already has the request `HeaderMap`; it is simply not surfaced onto the `StreamSlot` / exposed). This is the **only** crabscheme change `.26` requires; the cert-CN path and all crypto already work today.

### 5. Authorization — the load-bearing range-containment check

Per request, `.26` resolves the identity (§4) to a username, then calls the **pure** decision `auth-authorize?` (`src/auth.scm`, validated by the POC):

```
auth-authorize?(ctx, username, key, range_end, required):
  auth disabled              ⇒ ALLOW            ; the global flag short-circuits
  username = #f (no identity) ⇒ DENY            ; .26 → ErrUserEmpty / ErrInvalidAuthToken
  user holds the root role    ⇒ ALLOW            ; full access
  else                         ⇒ some permission of the user's roles COVERS [key, range_end) for `required`
```

`required` is **`READ` for `Range`/`Watch`**, **`WRITE` for `Put`/`DeleteRange`**; a **`READWRITE`** permission satisfies both. (A `Txn` checks each comparison key as `READ` and each inner op by its own type — `.26` walks the Txn; the per-op rule is unchanged.)

**Range-containment — the crux.** Canonicalize each `(key, range_end)` into a half-open interval `[lo, hi)` where `hi` is either a bytevector exclusive bound or `+∞` (the all-keys-from-key sentinel):

| `range_end` | interval `[lo, hi)` |
|---|---|
| empty / unset (single key) | `lo = key`, `hi = key‖0x00`  (covers exactly `{key}`) |
| `"\0"` (to end of keyspace) | `lo = key`, `hi = +∞`  (and `key = "\0"` ⇒ all keys: `lo = "\0"`) |
| otherwise (explicit / prefix) | `lo = key`, `hi = range_end` |

A permission interval `P = [plo, phi)` **covers** a request interval `R = [rlo, rhi)` iff:

```
plo ≤ rlo   AND   rhi ≤ phi          (with +∞ greater than every bytevector)
```

This is exactly the ADR-required rule — *"`pk ≤ k` and (`re ≤ pre` OR `pre` is the all-keys sentinel)"* — with the sentinel folded into `hi` so single-key, prefix, all-keys, and explicit ranges all fall out of **one** comparison. Appending `0x00` for a single key works because `[key, key‖0x00)` contains exactly `{key}` (`key‖0x00` is the immediate lexicographic successor). The union over a user's roles is **"some single permission covers the whole request"** — etcd does **not** stitch multiple permissions across one range request, and the POC asserts that two abutting perms `[a,m)+[m,z)` do **not** cover `Range [a,z)`.

Worked cases (all asserted in the POC):

- `READWRITE [a,c)` covers `GET/PUT a, b` but **denies** `c, d` (`c` is the exclusive end: `c‖0x00 ≤ c` is false).
- `READ [a,c)` covers `GET b` but **denies** `PUT b` (op-type).
- prefix `"foo"` = `[foo, fop)` covers `foo`, `foobar`; **denies** `fop` (the exclusive end) and `fo`.
- all-keys `[\0, +∞)` covers every single key and every range, including the all-keys range itself.
- a `Range [k, re)` is allowed only if one permission covers the whole `[k, re)`.

**Errors (etcd-faithful, what real clients match on).** On **deny**: gRPC **`PermissionDenied` (7)**, message `etcdserver: permission denied`. On **bad / missing auth** when auth is enabled: a missing/empty identity → `ErrUserEmpty` `etcdserver: user name is empty` (**`InvalidArgument`, 3**); a present-but-bad token → `ErrInvalidAuthToken` `etcdserver: invalid auth token` (**`Unauthenticated`, 16**). On a failed `Authenticate`: `ErrAuthFailed` `etcdserver: authentication failed, invalid user ID or password` (**`InvalidArgument`, 3**). On admin errors: `etcdserver: authentication is not enabled` / `user name already exists` / `user name not found` / `role name not found` etc. are **`FailedPrecondition` (9)**. `grpc-kv.scm` already defines `GRPC-OK 0` / `…UNAVAILABLE 14` / `…INTERNAL 13`; `.26`/`.27` add `GRPC-INVALID-ARGUMENT 3`, `GRPC-PERMISSION-DENIED 7`, `GRPC-FAILED-PRECONDITION 9`, `GRPC-UNAUTHENTICATED 16`.

## Alternatives considered

1. **Reserved prefix inside `NS-KEY`, written via `mvcc-put!`.** The "auth just rides the MVCC store" option the task floats. **Rejected** (§2): `mvcc-put!` emits a `NS-REV` Watch event and a full `Range` over all-keys would return the password hashes — auth would be enumerable/streamable to clients — and it couples auth to the keyspace `current-rev`. A dedicated `NS-AUTH` tag keeps the same replication/crash-consistency while staying invisible to `Range`/`Watch`, and matches etcd's separate-bucket + separate-`authRevision` design.
2. **JWT (stateless signed token).** Survives leader change with no token table and needs no replication. **Declined for v1** — etcd's default is the simple token table, which is less machinery and correct; a leader change just forces a re-`Authenticate`. The stdlib (`hmac-sha256`, `crypto-ed25519-sign`) already supports adding JWT later if cross-leader token validity is wanted. Recorded so `.26` doesn't have to rediscover it.
3. **Replicating the token table through Raft.** Makes tokens leader-independent, at the cost of a Raft round per `Authenticate` and GC of expired tokens in the state machine. **Rejected** — etcd's simple token is deliberately leader-local; the auth *state* (users/roles) is what must be replicated, and it is (§2). The token is a cheap leader-local cache.
4. **bcrypt to bit-match etcd.** **Rejected** — `(crab crypto)` ships Argon2id (OWASP's recommended successor); the stored hash is a self-describing PHC string, so the choice is internal and never crosses the wire. No reason to add a weaker primitive.
5. **Hashing on each replica in the apply-fn.** **Rejected** — Argon2id's random salt makes per-replica hashes differ, breaking determinism/snapshots. The leader hashes once and replicates the bytes (§3).

## Consequences

**Positive**

- The **load-bearing range-containment check is proven** over the real store (`test/auth-poc.scm`, 67/67, twice) before any enforcement is written — single-key / prefix / all-keys / range / op-type / union-doesn't-stitch / root / auth-disabled / deny all covered.
- **Replicated + leader-survivable for free:** auth state is one more namespace in the same Raft-committed, group-commit-fsync'd CF, so it inherits the substrate's Jepsen-validated crash-consistency and "applied identically on every replica" property — no new replication path.
- **No keyspace pollution / no disclosure:** `Range`/`Watch` never see auth records, and auth mutations never bump `current-rev` or emit Watch events (separate `auth-revision`), exactly like etcd.
- **Stronger-than-etcd password hashing** (Argon2id vs bcrypt) using a primitive that already ships and works.
- **Minimal surface added now:** only `src/auth.scm` (pure encoders/decoders + the check) and the POC; `.26`/`.27` are additive (new `mvcc-apply` cases + a gRPC service + one builtin).

**Negative / trade-offs**

- **One interpreter change is required** before `.26` can read the `token` header: a `grpc-request-metadata` builtin (§4). Until then only the cert-CN auth path is reachable end-to-end. (Filed as the explicit `.26` prerequisite.)
- **Tokens are leader-local:** a leadership change invalidates outstanding tokens and clients must re-`Authenticate` (etcd's simple-token behavior, not transparently HA). JWT (Alt 2) is the remedy if that ever matters.
- **Auth-record reads are point reads, not bounded MVCC scans.** Resolving a user's permissions does one `kv-get` per role; a pathological user with very many roles costs proportional `kv-get`s. Acceptable (role counts are tiny); a per-request identity→perms cache keyed by `auth-revision` is the obvious `.26` optimization if needed.
- **No per-record auth history.** Auth is "latest value + a global `auth-revision`" (etcd's model); there is no point-in-time read of "the user as of revision N". Not required by the etcd API.
